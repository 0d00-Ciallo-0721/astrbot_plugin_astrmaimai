# M7 审查报告：页面入口与管理端链路

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正结论口径，不修改业务代码。
- 旧版报告中“整体 Web 管理链不可发布”的说法需要收窄影响面。

## 当前有效的核心结论

### 1. standalone FastAPI backend 仍然存在真实断裂
以下问题当前仍然真实存在：

- `astrmai/webui/backend/routes/cognition_routes.py`
  - `_service()` 仍调用 `CognitionService(PluginApiAdapter(), get_db)`
  - 但 `CognitionService.__init__` 只接收 `plugin_api`
- `astrmai/webui/backend/routes/runtime_routes.py`
  - `_service()` 仍调用 `ObservabilityService(PluginApiAdapter(), get_db)`
  - 但 `ObservabilityService.__init__` 只接收 `plugin_api`
- `astrmai/webui/backend/routes/heartflow_routes.py`
- `astrmai/webui/backend/routes/learning_routes.py`
- `astrmai/webui/backend/routes/tools_routes.py`
  - 这三处 route 也都仍把 `get_db` 多传给只接收 `plugin_api` 的 service

额外核验到的当前真实问题：
- `tools_routes.py` 调用了 `recent_tool_traces()`，但 `toolsservice.py` 没有这个方法
- `learning_routes.py` 调用了 `run_reflect_once()`，但 `learningservice.py` 没有这个方法
- `cognition_routes.py` 里的部分方法转发，与 `CognitionService` 当前签名仍不匹配

### 2. Plugin Page 主入口不能和 standalone FastAPI 混为一谈
当前项目里真实存在两种不同入口理解：

- AstrBot Plugin Page 主入口
  - `main.py`
  - `astrmai/webui/plugin_pages.py`
- standalone FastAPI backend
  - `astrmai/webui/backend/server.py`
  - `astrmai/webui/backend/routes.py`

当前更准确的判断是：
- **standalone FastAPI backend 不能视为已修好**
- **AstrBot Plugin Page 主入口不应直接被上述 route/service 断裂等同判死**

## 修正后的影响判断

### 仍然可以保留的结论
- M7 中存在真实运行级问题
- backend route/service 断裂是当前仓库最明确的一组问题之一

### 需要删掉或收窄的结论
- 不应直接写成“当前整个页面入口与管理端链路都不可发布”
- 更准确的说法应为：
  - `standalone FastAPI backend` 不可视为可用
  - `Plugin Page` 主桥接链不等于这条 broken backend 链

## 当前建议优先级

### P1
- 修 route/service 构造参数断裂
- 修 route 调用了 service 中不存在的方法
- 修 `CognitionService` 转发签名不匹配

### P2
- 再重新区分哪些 backend route 真正仍需要保留
- 避免仓库里继续存在“主链路不走、但代码还挂着”的服务端残留

## 结论
- 旧版 M7 的问题本体不是错的
- 但旧版把影响面说大了
- 现在应将 M7 解释为：
  - `standalone FastAPI backend` 真实断裂
  - `Plugin Page` 主入口不应直接被一并判死
