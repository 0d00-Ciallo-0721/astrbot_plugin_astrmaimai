# M4：记忆与学习（Memory & Learning）

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- 本报告聚焦 `astrmai/learning/` 与 `astrmai/memory/` 的当前真实风险点，不把未验证的联动猜测直接写成当前阻断结论。

## 总体结论

M4 当前至少有两条仍然成立、且值得进入修复队列的真实问题：

- `evolution_manager.get_active_patterns_canonical()` 在异步上下文中的调用模型仍然脆弱
- `memory_write_service.should_skip_content()` 的内容过滤规则仍然过宽，会误杀合法内容

除此之外，memory / learning 联动链确实还存在验证盲区，但这条更适合作为后续补测或专项复核项，不应直接硬写成“当前已确认必炸”。

## 当前已确认的真实问题

### B1. `get_active_patterns_canonical()` 在运行中事件循环里会直接抛 `RuntimeError`
- 文件：
  - `astrmai/learning/evolution_manager.py:302`
- 相关函数：
  - `get_active_patterns_canonical(chat_id, limit=5)`
  - `get_active_patterns = get_active_patterns_canonical`
- 当前事实：
  - 代码会先取 `memory_engine.expression_pattern_service`
  - 如果 service 存在且带 `render_active_patterns(...)`
  - 它会先执行 `asyncio.get_running_loop()`
  - 一旦发现当前 loop 正在运行，就直接抛：
    - `RuntimeError("get_active_patterns should run in a worker thread when loop is active")`
  - 只有在没有活动事件循环时，才继续调用 `asyncio.run(...)`
- 触发条件：
  - 在异步上下文中同步调用 `get_active_patterns()` / `get_active_patterns_canonical()`
  - 例如后续如果某个 async service、async route、async UI 汇总链直接取活动表达模式摘要，就会触发这条路径
- 影响：
  - 旧报告里“在运行中的 loop 里直接 `asyncio.run()` 会炸”这个方向是对的
  - 但更准确的当前事实是：**它会更早地主动抛 `RuntimeError`**
  - 这依然属于真实运行时炸点，只是报错路径与旧说法不同
- 建议修复方向：
  - 明确把该能力改成 async API
  - 或者把同步 API 限定为只能在线程池 / 同步上下文使用，并在调用方做边界隔离

### B2. `should_skip_content()` 仍会误伤以 `{` 开头的正常文本内容
- 文件：
  - `astrmai/memory/services/memory_write_service.py:15`
- 相关函数：
  - `MemoryWriteService.should_skip_content(...)`
  - `MemoryWriteService.write(...)`
- 当前事实：
  - 过滤规则现在仍是：
    - 空文本直接跳过
    - 以 `{` 开头直接跳过
    - 以 ````json` 开头直接跳过
    - 含 `traceback`、`exception`、`all chat models fail`、`apitimesouterror` 等 token 也跳过
  - `write(...)` 一进入就依赖这条过滤逻辑
- 触发条件：
  - 写入内容恰好以 `{` 开头，但本质上不是噪音或异常日志
  - 比如模板化文本、结构化自然语言片段、用户原文引用、带花括号的普通陈述
- 影响：
  - 这会导致合法记忆内容被直接静默丢弃
  - 如果调用方没有显式追踪“为何被跳过”，就容易演化成“学习 / 记忆明明跑了，但后面查不到”的静默问题
- 建议修复方向：
  - 不要再用单纯的 `{` 前缀作为粗暴拒绝条件
  - 改成更精细的 JSON / 异常文本识别，或把“跳过原因”显式打点出来

## 当前仍值得保留、但尚未升级为已确认 bug 的观察项

### O1. memory / learning 联动链的可见性与降级透明度仍有验证盲区
- 关联区域：
  - `astrmai/learning/`
  - `astrmai/memory/services/`
- 当前事实：
  - 本轮复核确认了写入过滤和活动模式读取存在问题
  - 但还没有在同一条实链上证明“学习结果写入后一定无法被后续检索消费”
- 风险意义：
  - 这条不能直接写成“当前已确认断链”
  - 但它确实是 M4 最值得继续补实测的一条链路
- 建议：
  - 后续专项验证时，优先打通：
    - 学习产物生成
    - memory write
    - 索引/检索可见性
    - 下游 prompt 注入或行为消费

## 当前影响面结论

### 确认受影响
- 任何在 async 上下文里同步读取活动表达模式摘要的调用点
- 任何依赖 `MemoryWriteService` 持久化结构化文本内容的写入链

### 暂不应直接判死
- 整个 memory / learning 主域
- “学习产物绝对无法进入后续检索链”这一类更大的断链结论

## 修正后的最终结论
- 旧版关于 `asyncio.run()` 的描述需要更新，但它指向的风险本体仍然真实存在
- M4 当前最硬的两条问题是：
  1. `evolution_manager` 的同步包装 API 在 async 环境下会直接抛错
  2. `memory_write_service` 的过滤规则会误伤合法内容
- 后续如果要继续补成更完整的施工单，优先顺序建议如下：
  1. 先收 `get_active_patterns_canonical()` 的调用边界
  2. 再收 `should_skip_content()` 的误杀规则
  3. 最后再做 memory / learning 联动链专项补测
