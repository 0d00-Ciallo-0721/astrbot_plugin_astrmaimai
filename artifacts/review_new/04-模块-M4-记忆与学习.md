# M4：记忆与学习（Memory & Learning）

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- 本报告聚焦 `astrmai/learning/` 与 `astrmai/memory/` 的当前真实风险点，不把未验证的联动猜测直接写成当前阻断结论。

## 总体结论

M4 当前至少有两条仍然成立、且值得进入修复队列的真实问题：

- `evolution_manager.get_active_patterns_canonical()` 在异步上下文中的调用模型仍然脆弱
- `memory_write_service.should_skip_content()` 的 `{` 误杀规则已收口，但 memory / learning 联动链仍有待专项补测

除此之外，memory / learning 联动链确实还存在验证盲区，但这条更适合作为后续补测或专项复核项，不应直接硬写成“当前已确认必炸”。

## 当前已确认的真实问题

### B1. `get_active_patterns_canonical()` 的 async-safe 主路径已补齐，遗留 sync API 仅限同步上下文
- 文件：
  - `astrmai/learning/evolution_manager.py`
- 相关函数：
  - `get_active_patterns_canonical_async(chat_id, limit=5)`
  - `get_active_patterns_canonical(chat_id, limit=5)`
  - `get_active_patterns = get_active_patterns_canonical`
- 当前事实：
  - 代码会先取 `memory_engine.expression_pattern_service`
  - 如果 service 存在且带 `render_active_patterns(...)`
  - 新增 `get_active_patterns_canonical_async(...)` 直接 `await service.render_active_patterns(...)`
  - 现有同步包装 `get_active_patterns_canonical()` 只在没有活动事件循环时才继续调用 `asyncio.run(...)`
  - 如果在活动 loop 中误调同步包装，现在会抛出明确的 sync/async 边界错误，并指向 async API
- 触发条件：
  - 正式异步调用方未切到 `get_active_patterns_canonical_async(...)`
  - 遗留 async service / async route / async UI 汇总链如果继续误调同步包装，仍会命中边界错误
- 影响：
  - 正式异步读取路径上的直接运行时炸点已经收口
  - 剩余风险主要是遗留调用方仍把同步兼容 API 当成 async 入口使用
  - 这类误用现在会得到明确边界错误，而不是继续依赖 worker-thread 语义
- 建议修复方向：
  - 持续审计剩余调用点，优先统一切到 `get_active_patterns_canonical_async(...)`
  - 保留同步包装仅用于纯同步上下文兼容

### B2. `should_skip_content()` 的 `{` 误杀规则已收口，过滤边界改为异常 / 机器噪音载荷
- 文件：
  - `astrmai/memory/services/memory_write_service.py:15`
- 相关函数：
  - `MemoryWriteService.should_skip_content(...)`
  - `MemoryWriteService.write(...)`
- 当前事实：
  - 过滤规则现已改为：
    - 空文本直接跳过
    - 以 ````json` 开头的 fenced JSON 代码块直接跳过
    - 含 `traceback`、`exception`、`all chat models fail`、`apitimesouterror` 等 token 的异常噪音直接跳过
    - 仅当以 `{` 包裹的内容能被解析为 JSON object，且含 `error`、`errors`、`exception`、`traceback`、`stack`、`stacktrace`、`detail`、`details` 等异常字段时才跳过
  - 解析失败的 `{...` 文本、普通自然语言模板文本、不带异常字段的 JSON 风格业务内容都会继续写入
  - `write(...)` 仍在入口处复用该过滤逻辑，但现在会记录跳过原因，避免静默丢弃
- 触发条件：
  - 当前剩余风险主要不是 `{` 误杀本身，而是 memory / learning 联动链是否已有足够回归覆盖
- 影响：
  - 以 `{` 开头的合法记忆内容不再被粗暴丢弃
  - 跳过路径现在具备原因可观测性，便于排查写入为何未落库
- 建议修复方向：
  - 保持当前收窄后的过滤边界
  - 后续补测继续优先覆盖 memory write -> 检索 / 注入的联动可见性

## 当前仍值得保留、但尚未升级为已确认 bug 的观察项

### O1. memory / learning 联动链的可见性与降级透明度仍有验证盲区
- 关联区域：
  - `astrmai/learning/`
  - `astrmai/memory/services/`
- 当前事实：
  - 本轮复核确认了写入过滤和活动模式读取存在问题
  - 但还没有在同一条实链上证明“学习结果写入后一定无法被后续检索消费”
- 风险意义：
  - 这条不能直接写成“当前已确认断链”
  - 但它确实是 M4 最值得继续补实测的一条链路
- 建议：
  - 后续专项验证时，优先打通：
    - 学习产物生成
    - memory write
    - 索引/检索可见性
    - 下游 prompt 注入或行为消费

## 当前影响面结论

### 确认受影响
- 任何在 async 上下文里同步读取活动表达模式摘要的调用点
- 任何依赖 `MemoryWriteService` 持久化结构化文本内容的写入链

### 暂不应直接判死
- 整个 memory / learning 主域
- “学习产物绝对无法进入后续检索链”这一类更大的断链结论

## 修正后的最终结论
- `get_active_patterns_canonical()` 这条运行时炸点已通过 async 主路径 + sync-only 兼容包装收口
- M4 当前仍需优先处理的问题是：
  1. `memory_write_service` 的 `{` 误杀规则已收口，后续重点转为 memory / learning 联动补测
- 对 `evolution_manager` 而言，剩余风险主要是遗留 async 调用方继续误调同步兼容 API
- 后续如果要继续补成更完整的施工单，优先顺序建议如下：
  1. 先审计剩余调用点是否都已切到 `get_active_patterns_canonical_async()`
  2. 补齐 `should_skip_content()` 调整后的联动回归覆盖
  3. 最后再做 memory / learning 联动链专项补测
