# 全局审计：残留引用

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- 本报告区分三类对象：
  - 当前仍真实存在的重复定义残留
  - 仍存在但主要位于测试/兼容层的旧命名空间残留
  - 已经删除、不应继续写进当前残留统计的旧链路

## 总体结论

当前全局残留里最值得继续保留的，不是“还有大量运行时旧引用没清”，而是以下三类更准确的结论：

- `message_scope` 双副本是当前仍然真实存在的结构残留
- `astrmai.Heart / Brain / infra` 这类旧命名空间主要还残留在测试 helper 与兼容层，不等于当前生产代码正在错误导入
- 已删除的 standalone frontend / mock server / url validator 链路，不应继续算进“当前残留引用”

## 当前已确认的真实残留

### B1. `message_scope` 双副本是当前最明确的生产层残留
- 文件：
  - `astrmai/presentation/dto/message_scope.py`
  - `astrmai/conversation/contracts/message_scope.py`
- 当前事实：
  - 两处都定义了 `IngressDecision` / `MessageScope`
  - 当前生产调用更偏向 `presentation/dto/message_scope.py`
  - 本轮没有找到生产代码直接从 `conversation/contracts/message_scope.py` 导入这两个类
- 影响：
  - 它不是当前 `ImportError` 型故障
  - 但它确实是“一个概念有两个权威定义源”的真实结构残留
- 建议修复方向：
  - 保留一个权威定义
  - 另一个改为 re-export 或删除

### B2. 旧命名空间残留当前主要集中在测试 helper / 兼容层，而非生产主链
- 文件：
  - `tests/helpers/attention_stubs.py`
  - `tests/helpers/executor_stubs.py`
  - `tests/helpers/planner_stubs.py`
  - `tests/helpers/reply_engine_stubs.py`
  - `tests/helpers/state_bar_audit.py`
  - `tests/original_ported/*.py`
  - `tests/regression/architecture/test_import_boundaries_refactor.py`
- 当前事实：
  - 当前仍然能搜到：
    - `astrmai.Heart.*`
    - `astrmai.Brain.*`
    - `astrmai.infra.*`
  - 这些命名空间残留主要用于：
    - stub 注入
    - 历史迁移保护
    - import boundary 回归断言
  - 它们不等于当前生产代码在真实运行时仍依赖这些旧路径
- 影响：
  - 对代码阅读和自动扫描很容易造成误导
  - 如果下一个审查 agent 不区分“测试 stub 残留”和“生产导入残留”，就容易把问题范围说大
- 建议修复方向：
  - 在后续残留审查中，把“测试兼容残留”和“生产链残留”分开统计
  - 不要再把这批 helper 命名空间搜索结果直接当成生产 bug 数量

## 已确认应从当前残留统计中剔除的旧链路

### O1. 已删除的 standalone frontend / mock server / remote-image 旧链路，不应继续算作当前残留
- 当前已删除：
  - `astrmai/webui/frontend/`
  - `astrmai/webui/mock_frontend_server.py`
  - `astrmai/infrastructure/security/url_validator.py`
  - `REMOTE_IMAGE_ALLOWLIST.md`
- 当前事实：
  - 仓库里已经没有这些文件
  - 相关测试也已转向“文件不存在”或新主入口契约
- 结论：
  - 后续任何“残留引用”报告都不应继续把它们写成“当前仍存在的文件级残留”

## 当前影响面结论

### 确认受影响
- 结构权威定义的唯一性
- 自动审查与问题统计的准确性
- 测试兼容层与生产层问题边界

### 当前不应直接判死
- 生产主链存在大量旧路径导入
- standalone frontend / mock server / remote image 链仍在运行

## 修正后的最终结论
- 当前全局残留最值得继续跟的是：
  1. `message_scope` 双副本
  2. 测试兼容层里的旧命名空间残留统计方式
- 不应再继续跟的，是已经被删除的 standalone 旧链路
