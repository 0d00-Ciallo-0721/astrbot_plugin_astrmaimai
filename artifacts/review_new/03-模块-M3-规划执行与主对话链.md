# M3：规划、执行与主对话链

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- 本报告聚焦 `astrmai/conversation/planning/`、`execution/`、`loop/` 这条主对话链本身，不扩大到 WebUI 或基础设施子域。

## 总体结论

当前没有足够证据把 M3 判定为“主消息链整体断裂”。

但以下问题和结论当前仍值得保留：

- 存在一条已确认的真实实现缺陷：`semantic_chunk()` 仍是未接入且实现写法有误的死方法
- 存在一组低优先级兼容残留：主链代码仍保留旧 envelope / legacy extras 的兼容镜像
- 旧版“`heartflow_manager` 恒失效”的结论已经过时，后续修复不应再沿着这条方向投入

## 当前已确认的真实问题

### B1. `semantic_chunk()` 仍是未接入且实现写法有误的死方法
- 文件：
  - `astrmai/conversation/execution/text_segmenter.py:239`
- 相关函数：
  - `TextSegmenter.semantic_chunk(...)`
- 当前事实：
  - 当前全仓只找到该方法定义，没有找到生产调用方
  - 方法体里用于处理换行的正则仍写成 `r'\\n(#+\\s+)'` 和 `r'\\n{2,}'`
  - 这代表它匹配的是反斜杠加字母 `n`，而不是真实换行符
- 触发条件：
  - 未来有人把它接入 RAG 入库、长文切片、语义分块或任何新链路
- 影响：
  - 一旦被启用，分块边界会按错误规则工作
  - Markdown 标题前插入双换行、按双换行切块这套逻辑都不会按注释所说的方式生效
  - 但它目前没有进入主消息链，所以**当前运行期不是阻断级问题**
- 建议修复方向：
  - 如果打算继续保留：修正正则、补最小回归测试、再显式接入调用方
  - 如果短期不会用：直接删除或明确标注为废弃方法，避免未来被误接入

### B2. 主链仍保留一组 legacy compatibility mirror，当前更像维护负担而非运行阻断
- 文件：
  - `astrmai/conversation/planning/planner_prompt_context.py:8`
  - `astrmai/conversation/planning/planner_prompt_context.py:170`
  - `astrmai/conversation/planning/planner_prompt_context.py:424`
  - `astrmai/conversation/planning/planning_input_loader.py:152`
  - `astrmai/conversation/planning/planner_side_inputs.py:184`
  - `astrmai/conversation/execution/reply_artifact_builder.py:27`
  - `astrmai/conversation/execution/reply_artifact_builder.py:328`
  - `astrmai/conversation/execution/reply_service.py:30`
- 当前事实：
  - planning / execution 主链仍显式引用 `legacy_compat` 的读写桥接
  - 代码里还保留了 “Deprecated compatibility mirrors for legacy readers outside the main reply chain.” 这类注释
- 触发条件：
  - 新问题并不是“现在就会炸”
  - 真正的风险出现在后续继续重构 prompt / reply / event extras 时，维护者容易误判哪些字段仍必须保留
- 影响：
  - 这会让主链代码边界继续偏厚
  - 也会增加“明明主链已改造，但外部旧读取点仍靠兼容字段续命”的维护复杂度
  - 当前更适合作为 `P3` 级维护清理项，而不是当前运行级阻断
- 建议修复方向：
  - 为兼容层单独列出保留清单
  - 明确哪些 legacy extras 仍是对外契约，哪些只是历史镜像，可逐步下线

## 已确认过时、应从后续工单中剔除的旧结论

### O1. `heartflow_manager 恒为 None` 不再是当前真实问题
- 文件：
  - `astrmai/conversation/planning/planner.py:81`
  - `astrmai/proactive/proactive_task.py:222`
- 当前事实：
  - `Planner` 初始化时仍把 `self.heartflow_manager` 设为 `None`
  - 但 `proactive_task.configure(...)` 已会回填 `planner.heartflow_manager`
- 结论：
  - 旧报告把这条当成当前真实 bug 已不准确
  - 后续修复任务不应再把“heartflow manager 恒失效”列为 M3 当前问题

## 当前影响面结论

### 确认受影响
- `TextSegmenter.semantic_chunk()` 未来若被重新接入的任何新分块链路
- 规划 / 执行链上继续携带的 legacy compatibility 维护面

### 当前不应直接判死
- `main.py -> ingress -> attention -> planner -> executor -> reply` 这条主消息链
- 现有规划执行入口本身没有被本报告复核出“当前必炸”的直接证据

## 修正后的最终结论
- M3 当前最明确的真实问题不是“主链断裂”，而是：
  - 一个未接入但实现有误的死方法
  - 一组低优先级兼容残留
- 后续若要按工单修复，优先级建议如下：
  1. 先决定 `semantic_chunk()` 是修还是删
  2. 再单独整理 planning / execution 的 legacy compatibility 保留边界
  3. 不要再把 `heartflow_manager 恒失效` 当作当前待修项
