# M3：规划、执行与主对话链

## 说明
- 本报告已按当前仓库代码重新校正。
- 本轮已落实 Prompt 12 的结构收口与主链补测；报告同步更新到最新状态。
- 本报告聚焦 `astrmai/conversation/planning/`、`execution/`、`loop/` 这条主对话链本身，不扩大到 WebUI 或基础设施子域。

## 总体结论

当前没有足够证据把 M3 判定为“主消息链整体断裂”。

Prompt 12 已经收口掉此前最明确的一条结构性误导：

- `TextSegmenter.semantic_chunk()` 已从仓库中删除，不再以“未接入且实现错误”的状态继续留存

当前在 M3 范围内仍值得保留的，主要是：

- planning / execution 主链仍保留一组低优先级 legacy compatibility mirror
- 旧版“`heartflow_manager` 恒失效”的结论已经过时，后续修复不应再沿着这条方向投入

## 当前已确认的真实问题

### B1. 主链仍保留一组 legacy compatibility mirror，当前更像维护负担而非运行阻断
- 文件：
  - `astrmai/conversation/planning/planner_prompt_context.py`
  - `astrmai/conversation/planning/planning_input_loader.py`
  - `astrmai/conversation/planning/planner_side_inputs.py`
  - `astrmai/conversation/execution/reply_artifact_builder.py`
  - `astrmai/conversation/execution/reply_service.py`
- 当前事实：
  - planning / execution 主链仍显式引用 `legacy_compat` 的读写桥接
  - 代码里仍保留 “Deprecated compatibility mirrors for legacy readers outside the main reply chain.” 一类兼容语义
- 触发条件：
  - 新问题并不是“现在就会炸”
  - 真正的风险出现在后续继续重构 prompt / reply / event extras 时，维护者容易误判哪些字段仍必须保留
- 影响：
  - 这会让主链代码边界继续偏厚
  - 也会增加“明明主链已改造，但外部旧读取点仍靠兼容字段续命”的维护复杂度
  - 当前更适合作为 `P3` 级维护清理项，而不是当前运行级阻断
- 建议修复方向：
  - 为兼容层单独列出保留清单
  - 明确哪些 legacy extras 仍是对外契约，哪些只是历史镜像，可逐步下线

## 已确认已收口、应从后续工单中剔除的旧结论

### O1. `semantic_chunk()` 不再是当前仓库中的真实问题
- 文件：
  - `astrmai/conversation/execution/text_segmenter.py`
- 当前事实：
  - Prompt 12 已直接删除 `TextSegmenter.semantic_chunk(...)`
  - 当前全仓不再保留这条未接入且实现错误的死方法
- 结论：
  - 后续 M3 工单不应再把“`semantic_chunk()` 死且错”写成当前待修项

### O2. `heartflow_manager 恒为 None` 不再是当前真实问题
- 文件：
  - `astrmai/conversation/planning/planner.py`
  - `astrmai/proactive/proactive_task.py`
- 当前事实：
  - `Planner` 初始化时仍把 `self.heartflow_manager` 设为 `None`
  - 但 `proactive_task.configure(...)` 已会回填 `planner.heartflow_manager`
- 结论：
  - 旧报告把这条当成当前真实 bug 已不准确
  - 后续修复任务不应再把“heartflow manager 恒失效”列为 M3 当前问题

## 当前影响面结论

### 确认受影响
- 规划 / 执行链上继续携带的 legacy compatibility 维护面

### 当前不应直接判死
- `main.py -> ingress -> attention -> planner -> executor -> reply` 这条主消息链
- 现有规划执行入口本身没有被本报告复核出“当前必炸”的直接证据

## 修正后的最终结论
- M3 当前最明确的真实问题，不再是 `semantic_chunk()`，而是主链周边仍保留的一组低优先级兼容镜像
- Prompt 12 已完成这轮应做的结构收口：删除误导性死方法，并补上入口级最小 smoke
- 后续若要继续推进 M3，优先级建议如下：
  1. 单独整理 planning / execution 的 legacy compatibility 保留边界
  2. 不要再把 `semantic_chunk()` 或 `heartflow_manager 恒失效` 当作当前待修项
