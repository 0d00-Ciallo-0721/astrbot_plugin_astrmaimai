# M9：测试与运行验证契约

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- 本报告的目标不是否定当前测试价值，而是指出“哪些地方测试全绿仍不能自动推出真实运行无风险”。

## 总体结论

M9 当前最真实的问题不是“测试全都不可信”，而是存在以下三类结构性盲区：

- 主插件入口与完整主消息链缺少直接打穿的端到端验证
- 大量测试依赖 stub / fake module / `original_ported` 兼容层，语义更偏迁移保护而非真实运行验证
- Plugin Page 相关验证大量基于 fixture bridge stub，而不是真正的 AstrBot 宿主页面环境

## 当前已确认的真实问题

### B1. 主插件入口与完整消息主链缺少直接端到端覆盖
- 相关入口：
  - `main.py`
  - `PluginFacade.on_global_message()`
  - `ingress -> attention -> planner -> executor -> reply`
- 当前事实：
  - 当前能看到关于主入口的测试更多集中在：
    - `tests/test_main_reverse_session_hook_refactor.py`
    - `tests/integration/host/test_host_mock_validation.py`
  - 这些测试覆盖了注册钩子、`on_llm_request`、`event_message_type` 等片段
  - 但本轮没有找到一条测试把：
    - `main.py`
    - `PluginFacade.on_global_message()`
    - ingress / attention / planner / executor / reply
    作为单条事件流完整打穿
- 触发条件：
  - 这不是单测会失败的问题
  - 风险在于：多个局部测试都绿时，仍可能遗漏“真实链路拼接处”的参数、extra、状态传递问题
- 影响：
  - 测试全绿不能自动推出“主插件实跑一定没问题”
  - 对后续主链重构尤其敏感
- 建议补测方向：
  - 增加一条最小主消息端到端测试
  - 至少把 `main.py -> PluginFacade.on_global_message() -> reply` 这条链真实串起来

### B2. stub / fake module / `original_ported` 路径仍构成测试语义盲区
- 文件：
  - `tests/helpers/astrbot_stubs.py`
  - `tests/helpers/attention_stubs.py`
  - `tests/helpers/executor_stubs.py`
  - `tests/helpers/planner_stubs.py`
  - `tests/helpers/reply_engine_stubs.py`
  - `tests/original_ported/helpers.py`
  - `tests/original_ported/*.py`
- 当前事实：
  - 当前测试体系大量依赖 `install_astrbot_stubs(...)` 及一系列 helper stubs
  - `tests/original_ported/` 仍保留整套迁移保护测试
  - 一些 helper 还会显式注入旧命名空间，例如：
    - `astrmai.Heart.*`
    - `astrmai.Brain.*`
    - `astrmai.infra.*`
- 触发条件：
  - 这不会直接让生产代码出错
  - 风险在于：测试通过时，覆盖到的是“被 stub 过的环境”而不一定是真实宿主与真实依赖接线
- 影响：
  - 某些测试更像“兼容迁移保护”而不是“当前运行路径验收”
  - 这会降低“绿测 == 真正可运行”的说服力
- 建议修复方向：
  - 给测试分层打标签：
    - 迁移保护
    - 结构契约
    - 真实运行路径验证
  - 不要把 stub 驱动测试和真实入口验收混为一谈

### B3. Plugin Page 相关验证大量基于 fixture bridge stub，而不是真实宿主页面
- 文件：
  - `tests/helpers/scheduler_webui_fixture_server.py:62`
  - `tests/helpers/scheduler_webui_fixture.py:838`
  - `tests/test_scheduler_fixture_refactor.py:119`
- 当前事实：
  - fixture server 会直接把 `/pages/admin` 挂到本地静态目录
  - fixture 页面 `ready()` 返回的是：
    - `mode: "fixture_stub"`
  - 当前这套验证更像“本地桥接后的插件页壳体验证”
  - 而不是真正嵌入 AstrBot 宿主页后的真实 host 交互验证
- 触发条件：
  - 不是说现有测试无效
  - 而是它天然无法覆盖宿主 iframe、宿主权限、宿主注入对象这类真实页面边界问题
- 影响：
  - Plugin Page 相关测试绿了，只能证明“fixture bridge 模式可用”
  - 不能完全等同于“真实 AstrBot 插件页环境已验收完毕”
- 建议补测方向：
  - 如果后续还要提高把握度，至少补一条真实宿主页容器下的 smoke 验证

## 已确认应从后续测试结论中剔除的旧前提

### O1. 已删除旧链路不应继续作为当前测试判断前提
- 已删除链路：
  - `astrmai/webui/frontend/`
  - `astrmai/webui/mock_frontend_server.py`
  - `astrmai/infrastructure/security/url_validator.py`
- 结论：
  - 后续测试与审查不应继续把这几条旧链路视为“当前仍需覆盖的运行对象”

## 当前影响面结论

### 确认受影响
- “测试全绿是否足以证明插件真实可运行”这件事的可信度
- 主链路、Plugin Page、宿主集成的最终验收口径

### 当前不应直接判死
- 现有全部测试资产
- 现有测试全部失去价值这种扩大化结论

## 修正后的最终结论
- M9 当前的核心问题是“验证盲区”，不是“测试体系整体失效”
- 后续补测优先级建议如下：
  1. 先补主插件入口到主消息链的最小端到端验证
  2. 再把 stub/ported 测试与真实运行验证测试分层
  3. Plugin Page 若要继续提高把握度，再补真实宿主页 smoke 验证
