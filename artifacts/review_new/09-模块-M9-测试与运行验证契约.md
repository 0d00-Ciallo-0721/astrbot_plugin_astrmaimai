# M9：测试与运行验证契约

## 说明
- 本报告已按当前仓库代码重新校正。
- 本轮已落实 Prompt 12 的最小主链补测；报告同步更新到最新状态。
- 本报告的目标不是否定当前测试价值，而是指出“哪些地方测试全绿仍不能自动推出真实运行无风险”。

## 总体结论

M9 当前最真实的问题仍然是“验证盲区”，但 Prompt 12 已经收窄了其中最关键的一块入口盲区：

- 已新增一条最小主消息链 smoke，能够真实经过 `main.py -> PluginFacade.on_global_message() -> yield reply`
- 但大量测试依赖 stub / fake module / `original_ported` 兼容层的语义盲区仍在
- Plugin Page 相关验证仍主要基于 fixture bridge stub，而不是真正的 AstrBot 宿主页环境

## 当前已确认的真实情况

### S1. 主插件入口已补上最小 smoke，但仍不是完整宿主级或 planner/executor 全链验收
- 相关入口：
  - `main.py`
  - `PluginFacade.on_global_message()`
  - `presentation.events.message_entry.handle_global_message()`
  - `tests/integration/host/test_host_mock_validation.py`
- 当前事实：
  - Prompt 12 已新增一条最小 smoke，把 `main.AstrMaiPlugin.on_global_message()`、`PluginFacade.on_global_message()` 和入口层 `yield reply` 真实串起来
  - 这条测试可以证明：主插件入口包装层没有明显断点，主链基本事件流能从入口打到可见回复
- 仍未覆盖的边界：
  - 它不是完整 AstrBot 宿主页环境下的真实运行验证
  - 它也没有把 `planner -> executor -> reply service` 的全部内部运行路径做成全链路 E2E
- 影响：
  - 入口级盲区已经被补上一条最小证据
  - 但“主链已经全量验收完毕”这个结论仍然不能成立

### B1. stub / fake module / `original_ported` 路径仍构成测试语义盲区
- 文件：
  - `tests/helpers/astrbot_stubs.py`
  - `tests/helpers/attention_stubs.py`
  - `tests/helpers/executor_stubs.py`
  - `tests/helpers/planner_stubs.py`
  - `tests/helpers/reply_engine_stubs.py`
  - `tests/original_ported/helpers.py`
  - `tests/original_ported/*.py`
- 当前事实：
  - 当前测试体系仍大量依赖 `install_astrbot_stubs(...)` 及一系列 helper stubs
  - `tests/original_ported/` 仍保留整套迁移保护测试
  - 一些 helper 还会显式注入旧命名空间，例如：
    - `astrmai.Heart.*`
    - `astrmai.Brain.*`
    - `astrmai.infra.*`
- 影响：
  - 某些测试更像“兼容迁移保护”而不是“当前运行路径验收”
  - 这会降低“绿测 == 真正可运行”的说服力
- 建议修复方向：
  - 给测试分层打标签：
    - 迁移保护
    - 结构契约
    - 真实运行路径验证
  - 不要把 stub 驱动测试和真实入口验收混为一谈

### B2. Plugin Page 相关验证大量基于 fixture bridge stub，而不是真实宿主页面
- 文件：
  - `tests/helpers/scheduler_webui_fixture_server.py`
  - `tests/helpers/scheduler_webui_fixture.py`
  - `tests/test_scheduler_fixture_refactor.py`
- 当前事实：
  - fixture server 会直接把 `/pages/admin` 挂到本地静态目录
  - fixture 页面 `ready()` 返回的是：
    - `mode: "fixture_stub"`
  - 当前这套验证更像“本地桥接后的插件页壳体验证”
  - 而不是真正嵌入 AstrBot 宿主页后的真实 host 交互验证
- 影响：
  - Plugin Page 相关测试绿了，只能证明“fixture bridge 模式可用”
  - 不能完全等同于“真实 AstrBot 插件页环境已验收完毕”
- 建议补测方向：
  - 如果后续还要提高把握度，至少补一条真实宿主页容器下的 smoke 验证

## 已确认应从后续测试结论中剔除的旧前提

### O1. “主插件入口完全没有直接打穿验证”已不再准确
- 结论：
  - Prompt 12 已补上一条最小入口 smoke
  - 后续报告不应再把“入口级完全无直接覆盖”写成当前事实

### O2. 已删除旧链路不应继续作为当前测试判断前提
- 已删除链路：
  - `astrmai/webui/frontend/`
  - `astrmai/webui/mock_frontend_server.py`
  - `astrmai/infrastructure/security/url_validator.py`
- 结论：
  - 后续测试与审查不应继续把这几条旧链路视为“当前仍需覆盖的运行对象”

## 当前影响面结论

### 确认受影响
- “测试全绿是否足以证明插件真实可运行”这件事的可信度
- 主链路、Plugin Page、宿主集成的最终验收口径

### 当前不应直接判死
- 现有全部测试资产
- 现有测试全部失去价值这种扩大化结论

## 修正后的最终结论
- M9 当前的核心问题仍是“验证盲区”，不是“测试体系整体失效”
- Prompt 12 已经补上入口级最小 smoke，因此主链验收可信度较此前更高
- 但若要继续提高把握度，后续优先级建议如下：
  1. 把 stub/ported 测试与真实运行验证测试继续分层
  2. 如需更高主链信心，再补真实宿主或更深 planner/executor 路径的验收
  3. Plugin Page 若要继续提高把握度，再补真实宿主页 smoke 验证
