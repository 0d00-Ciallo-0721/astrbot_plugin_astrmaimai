# M6：基础设施与运行时支撑

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- M6 范围很大，本报告只保留当前能直接从代码确认的基础设施风险，不再沿用旧版“整体 blocking”口径。

## 总体结论

当前最值得保留的 M6 问题，不是“整层基础设施都不稳”，而是以下两类更具体的工单：

- `persistence_schema.py` 的数据库兼容迁移仍是条件性异常面
- `PersistenceSchemaMixin` 里有一段明显未接入的索引去重辅助函数，容易让维护者误以为初始化链已做 reload 去重保护

此外，M6 还会被配置链断裂实质影响，但这条根因主要属于 M1 / C3，而不是 M6 自身定义错误。

## 当前已确认的真实问题

### B1. `persistence_schema.py` 的兼容迁移仍只对“重复列”这一类异常做了窄处理
- 文件：
  - `astrmai/infrastructure/persistence/persistence_schema.py:47`
  - `astrmai/infrastructure/persistence/persistence_schema.py:187`
- 相关函数：
  - `_init_db_sync()`
  - `_init_db()`
- 当前事实：
  - sync / async 两条初始化路径都内联了大量 `ALTER TABLE ... ADD COLUMN ...`
  - 对这些迁移语句的异常处理，当前都只显式吞掉：
    - `"duplicate column name"`
  - 一旦遇到其他结构偏差，例如：
    - 目标表不存在
    - 列类型不兼容
    - 历史库结构偏差超出“只差几列”这个假设
  - 当前逻辑就会直接抛出并走最外层 `logger.error(...)`
- 触发条件：
  - 旧库结构异常
  - 半迁移状态数据库
  - 用户手工改过表结构
  - 测试环境和生产环境 schema 历史不一致
- 影响：
  - 这类风险是“条件性启动异常”，不是“常态必炸”
  - 但一旦命中，初始化迁移失败会直接影响持久化与运行时状态层
- 建议修复方向：
  - 把兼容迁移从“纯字符串 `ALTER TABLE` 列补丁”升级成更明确的 schema 检查
  - 至少把“表不存在 / 列异常 / 历史偏差”区分开记录，不要都收敛成一条笼统错误日志

### B2. `_dedupe_sqlmodel_metadata_indexes()` 当前是未接入的死辅助函数
- 文件：
  - `astrmai/infrastructure/persistence/persistence_schema.py:11`
- 相关函数：
  - `_dedupe_sqlmodel_metadata_indexes()`
- 当前事实：
  - 函数定义存在
  - 但当前仓库里没有任何调用点
- 触发条件：
  - 不是运行时立即触发的问题
  - 风险来自维护层：阅读代码的人容易以为初始化前已经做了 reload 后的 metadata index 去重
- 影响：
  - 如果这个函数本来是为“热重载后 SQLModel metadata index 重复”准备的防护，那么当前这层防护实际上并未生效
  - 这更像“代码意图与实际接线不一致”的维护风险
- 建议修复方向：
  - 如果确实需要这层防护，就显式接入初始化链
  - 如果已经不需要，就删除该辅助函数，避免误导

## 当前已确认的关联影响

### A1. M6 会被配置链断裂实质影响，但根因不在 M6
- 关联文件：
  - `config.py`
  - `_conf_schema.json`
  - `astrmai/app/bootstrap.py`
  - `astrmai/shared/constants/defaults.py`
- 当前事实：
  - 运行时基础设施设置依赖配置对象回填
  - 若配置链断裂，M6 会被动落回默认值
- 影响：
  - gateway / lane / feature flag 等运行时行为可能不按用户配置生效
- 定位建议：
  - 这条不应在 M6 单独闭环
  - 应与 `10-交叉链路-C3-配置链验证.md` 联动修复

## 当前影响面结论

### 确认受影响
- 持久化 schema 兼容迁移链
- reload / metadata 初始化保护的可维护性

### 当前不应直接判死
- 整个 `astrmai/infrastructure/` 层
- gateway / runtime / persistence 全域都存在阻断级问题这类扩大化说法

## 修正后的最终结论
- M6 当前最真实的问题是“条件性迁移异常面”和“未接入的去重辅助函数”
- 后续修复优先级建议如下：
  1. 先收 `persistence_schema.py` 的迁移异常分层与健壮性
  2. 再决定 `_dedupe_sqlmodel_metadata_indexes()` 是接线还是删除
  3. 配置落默认值这条，回到 C3 总链路处理，不要在 M6 单独误判根因
