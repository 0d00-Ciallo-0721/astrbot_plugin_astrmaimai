# M6：基础设施与运行时支撑

## 说明
- 本报告已按当前仓库代码重新校正。
- 仅修正报告结论，不修改业务代码。
- M6 范围很大，本报告只保留当前能直接从代码确认的基础设施风险，不再沿用旧版“整体 blocking”口径。

## 总体结论

本窗口针对 M6 的两条直接 persistence 工单已完成收口：

- `persistence_schema.py` 不再只靠“吞 duplicate column name”这一层脆弱假设
- `_dedupe_sqlmodel_metadata_indexes()` 的真实归宿已经核实，并保留了回归证明

此外，M6 还会被配置链断裂实质影响，但这条根因主要属于 M1 / C3，而不是 M6 自身定义错误。

## 本轮已完成收口的历史问题

### B1. `persistence_schema.py` 的兼容迁移异常面已做分层收口
- 文件：
  - `astrmai/infrastructure/persistence/persistence_schema.py:42`
  - `astrmai/infrastructure/persistence/persistence_schema.py:79`
  - `astrmai/infrastructure/persistence/persistence_schema.py:217`
- 相关函数：
  - `_apply_schema_patch_sync()`
  - `_apply_schema_patch_async()`
  - `_init_db_sync()`
  - `_init_db()`
- 当前事实：
  - sync / async 两条初始化路径已复用统一 schema patch helper
  - 对兼容迁移语句的异常处理现在只对以下场景显式吞掉：
    - `"duplicate column name"`
  - 一旦遇到其他结构偏差，例如：
    - 目标表不存在
    - 列类型不兼容
    - 历史库结构偏差超出“只差几列”这个假设
  - 当前逻辑会把具体 scope、失败 SQL 和原始 sqlite 错误拼进诊断消息，再走最外层 `logger.error(...)`
- 当前判断：
  - “只会吞 duplicate column name，其他异常难以定位”的历史问题已收口
  - 当前剩余行为是“失败即明确报错并终止该次初始化”，符合本窗口最小修复目标

### B2. `_dedupe_sqlmodel_metadata_indexes()` 已接入初始化链，当前不构成独立故障
- 文件：
  - `astrmai/infrastructure/persistence/persistence_schema.py:11`
- 相关函数：
  - `_dedupe_sqlmodel_metadata_indexes()`
- 当前事实：
  - 函数定义存在
  - 但当前仓库里已经在 `PersistenceManager.__init__()` 中调用
  - 相关回归测试已能证明 reload 后的重复索引会被收口
- 触发条件：
  - 不是运行时立即触发的问题
  - 维护风险主要来自“以为它没接线”或后续误删
- 影响：
  - 当前这层防护是生效的
  - 更像“有用的初始化防护，需要保留回归证明”的维护点
- 建议修复方向：
  - 保留现有接线和回归测试
  - 若后续确认没有任何副作用，再考虑删除，但不要按“未接线”方向处理

## 当前已确认的关联影响

### A1. M6 会被配置链断裂实质影响，但根因不在 M6
- 关联文件：
  - `config.py`
  - `_conf_schema.json`
  - `astrmai/app/bootstrap.py`
  - `astrmai/shared/constants/defaults.py`
- 当前事实：
  - 运行时基础设施设置依赖配置对象回填
  - 若配置链断裂，M6 会被动落回默认值
- 影响：
  - gateway / lane / feature flag 等运行时行为可能不按用户配置生效
- 定位建议：
  - 这条不应在 M6 单独闭环
  - 应与 `10-交叉链路-C3-配置链验证.md` 联动修复

## 当前影响面结论

### 确认受影响
- 持久化 schema 兼容迁移链的历史脆弱点已收口

### 当前不应直接判死
- 整个 `astrmai/infrastructure/` 层
- gateway / runtime / persistence 全域都存在阻断级问题这类扩大化说法
- reload / metadata 初始化保护当前不应再按“死辅助函数”误判

## 修正后的最终结论
- 本窗口已关闭 M6 在 `persistence_schema.py` 上的直接历史问题。
- 索引去重 helper 已接线，且已有回归证明，不应再视作未接入缺陷。
- M6 剩余需要继续关注的内容是配置落默认值这类跨链路问题，应回到 C3 总链路处理，不应在本窗口扩大解释为 persistence 子系统未收口。
