# README：提示词执行顺序说明

## 用途
本目录下的 `01-12` 提示词不是按报告编号机械拆分，而是按“当前真实问题的修复顺序”组织。

推荐你把它们按编号顺序逐个发给 DeepSeek 执行。

每一轮都应满足：
- 先读该提示词里列出的报告和代码
- 只修该轮范围内的问题
- 跑该轮要求的最小验证
- 修完后同步更新对应报告
- 再进入下一轮

不要跳轮，也不要把多轮任务混在一次调用里一起做。

## 总体顺序

### 第一阶段：先收最核心配置与 backend 断裂
1. `01-配置链核心断裂修复.md`
2. `02-配置链补完与可配置参数收口.md`
3. `03-Standalone-Backend构造签名断裂修复.md`
4. `04-Standalone-Backend方法签名与死路由收口.md`

这一阶段完成后，应该优先解决：
- 配置 schema / Pydantic / 调用方 三段断裂
- standalone backend 最明显的 route/service 断裂

### 第二阶段：再收状态与运行时真实炸点
5. `05-FrequencyController并发保护修复.md`
6. `06-GroupReplyWaitManager并发保护修复.md`
7. `07-WakeupService配置防护修复.md`
8. `08-EvolutionManager异步上下文运行时修复.md`
9. `09-MemoryWriteService过滤误杀修复.md`

这一阶段完成后，应该优先解决：
- 并发共享状态保护不足
- 条件性运行时异常
- 记忆写入误杀

### 第三阶段：最后做结构收口与验收补测
10. `10-注意力链空值防护与冗余清理.md`
11. `11-PersistenceSchema健壮性与死辅助函数收口.md`
12. `12-结构收口与主链验收补测.md`

这一阶段完成后，目标是：
- 收口剩余中低优先级真实问题
- 提升主链验收可信度
- 收敛最终报告

## 每轮执行规则

### 规则 1
必须按当前提示词指定的“必读报告 + 必读代码”开始，不要跳过阅读直接改。

### 规则 2
如果提示词里的问题已经被前一轮修掉，要先核对当前代码，再决定：
- 更新提示词里对应目标的状态
- 不重复修已经关闭的问题

### 规则 3
每一轮只做当前提示词范围内的工作，不顺手做下一轮。

### 规则 4
每一轮结束后，至少更新该提示词点名要求同步更新的报告文件。

### 规则 5
如果本轮修复导致总判断变化，顺手更新：
- `artifacts/review_new/13-汇总-AstrMai最终审查报告.md`

## DeepSeek 使用建议

### 建议发法
你可以直接一次发一份提示词内容给 DeepSeek。

推荐格式：
1. 先贴该提示词全文
2. 再补一句：
   - “严格按提示词范围执行，只修改相关代码与报告，不要扩大改动范围”
3. 修完后再发下一份

### 不建议发法
不要把 `01-12` 一次性全部丢给它。

原因：
- 容易扩大改动范围
- 容易重复修同一块
- 容易把报告口径和代码状态重新搞乱

## 推荐验收节奏

### 小节奏
每完成 1 份提示词：
- 看它是否完成了提示词中的“完成标准”
- 看对应报告是否更新

### 中节奏
每完成一个阶段：
- 跑一次该阶段相关测试
- 快速复读 `13-汇总-AstrMai最终审查报告.md`

### 大节奏
完成 `12` 之后：
- 做一次总复核
- 重写或更新最终总报告

## 当前最关键的依赖关系

### `01` 先于 `02`
因为 `02` 是配置链补完，前提是 `conversation` 和 `deep_temporal_* / maintenance_*` 主断裂先收住。

### `03` 先于 `04`
因为要先修 route/service 构造参数断裂，再修 route 调用的方法与签名问题。

### `05/06/07` 先于 `12`
因为 `12` 是最后结构收口与验收补测，不应该在并发与运行时真实炸点未收口前提前做。

### `08/09` 先于 `12`
因为 memory / learning 仍是总报告里的真实问题，应该先修完再做最终验收。

## 最终目标
当 `01-12` 全部完成后，理想状态应是：
- 高优先级真实 bug 已处理
- 中优先级结构问题已收口
- 主消息链至少补上最小验收测试
- `13-汇总-AstrMai最终审查报告.md` 能重新代表最新真实状态
