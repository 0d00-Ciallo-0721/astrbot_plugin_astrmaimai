## 🔴 Blocking

### B1. `_conf_schema.json` 的 `conversation` 段在 Pydantic 模型中完全缺失

**文件**: `config.py` — `AstrMaiConfig` 类；`_conf_schema.json` — "conversation" 节 (L168-279)

`_conf_schema.json` 定义了一个包含 11 个字段的 `conversation` 配置对象（`enable_dialogue_store`, `enable_context_compaction`, `enable_prefix_caching`, `hot_zone_ttl_seconds`, `warm_zone_ttl_seconds`, `warm_zone_max_tokens`, `compaction_provider_id`, `compaction_trigger_segments`, `compaction_trigger_tokens`, `compaction_keep_recent_segments`, `compaction_summary_max_tokens`），但 `AstrMaiConfig` 没有任何 `conversation` 字段。

后果链：

1. **`build_infrastructure_settings()`** (`astrmai/shared/constants/defaults.py:80-82`) 中 `getattr(config, "conversation", None)` 永远为 `None` → 三个 feature flag 永远走硬编码默认值 True，无视用户配置
2. **`bootstrap.py` `_build_state_dialogue_services()`** (L170) 的 `conversation_settings = getattr(runtime.config, "conversation", None)` 永远为 `None` → 所有 `getattr(conversation_settings, ...)` 调用用 fallback 而非用户值
3. **`bootstrap.py` `_build_context_compaction_service()`** (L201-212) 同理

**修复**: 在 `config.py` 中新增 `ConversationConfig` Pydantic 模型，并在 `AstrMaiConfig` 中加入 `conversation: ConversationConfig = Field(default_factory=ConversationConfig)`。字段名需与 schema 一致。

---

### B2. `deep_temporal_*` 与 `maintenance_*` 字段位于 Schema 错误命名空间下

**文件**: `_conf_schema.json` L60-95（位于 `global_settings.items` 下）vs `config.py` `MemoryConfig` 类 L98-110

以下 9 个字段在 schema 中被放在 `global_settings` 下，但 Pydantic 模型放在了 `MemoryConfig` 中：

| 字段 | Schema 位置 | 模型位置 |
|------|------------|---------|
| `deep_temporal_alpha` | `global_settings` | `memory` |
| `deep_temporal_tau_seconds` | `global_settings` | `memory` |
| `deep_temporal_lambda_default` | `global_settings` | `memory` |
| `deep_temporal_lambda_fact` | `global_settings` | `memory` |
| `deep_temporal_candidate_pool_factor` | `global_settings` | `memory` |
| `deep_temporal_candidate_pool_min` | `global_settings` | `memory` |
| `deep_temporal_llm_window` | `global_settings` | `memory` |
| `maintenance_hot_beta` | `global_settings` | `memory` |
| `maintenance_temporal_stale_hot_threshold` | `global_settings` | `memory` |

用户在 WebUI 配置界面中通过 schema 的 `global_settings` 组设置这些值，但 Pydantic 模型在反序列化时只会从 `memory` 段读取 → **用户配置静默丢失**。

**修复**: 将这些字段从 schema 的 `global_settings` 移至 `memory` 段下，或从 Pydantic 的 `MemoryConfig` 中删除并在 `GlobalSettingsConfig` 中新增。

## 🟡 Should-fix

### S1. Schema 缺少 `performance` 段

**文件**: `config.py` `PerformanceConfig` (L25-27) vs `_conf_schema.json`

`config.py` 定义了 `PerformanceConfig(summary_threshold: int = 300)`，但 `_conf_schema.json` 中没有 `performance` 段。用户无法通过 WebUI 配置 `summary_threshold`。

**修复**: 在 schema 中增加 `performance` 配置段。

---

### S2. Schema evolution 段缺少 `jargon_min_count`

**文件**: `config.py` `EvolutionConfig.jargon_min_count` (L100) vs `_conf_schema.json` evolution 节

`EvolutionConfig` 有 `jargon_min_count: int = 2`，但 schema 的 evolution 段未包含该字段。

**修复**: 在 schema evolution 节中补充 `jargon_min_count`。

---

### S3. Schema 描述字符串存在编码损坏（mojibake）

**文件**: `_conf_schema.json` L60-95

`deep_temporal_*` 和 `maintenance_*` 字段的 `description` 字符串明显是 GBK/GB2312 编码被以 UTF-8 解码后的乱码：

```
"description": "deep retrieval 鏃堕棿浠叉潈淇濆簳绯绘暟"  # 应为 "时间衰减权重保底系数"
"description": "deep retrieval 鍊欓€夋睜鏈€灏忔潯鏁?"      # 应为 "候选池最小条数"
```

这些乱码显示在 WebUI 配置界面中会让用户完全看不懂。

**修复**: 用正确的 UTF-8 编码重写这些 description 字符串。

## 🔵 Nits

### N1. Schema 默认值与代码 fallback 值不一致

**文件**: `_conf_schema.json` conversation 段 vs `bootstrap.py` L202-210

当 `conversation_settings` 为 `None`（当前因 B1 恒为 None）时，bootstrap.py 使用的 fallback 默认值与 schema 中声明的默认值不一致：

| 字段 | Schema 默认值 | 代码 fallback |
|------|--------------|---------------|
| `compaction_trigger_segments` | 30 | 40 |
| `compaction_keep_recent_segments` | 12 | 16 |

即使修复了 B1（新增 `ConversationConfig`），Pydantic 模型的默认值也应当与 schema 保持一致。建议统一到 schema 的默认值。

---

### N2. `track_incoming_user_activity` 中协程包装方式正确但易误解

**文件**: `plugin_facade.py` L190-192

```python
def track_incoming_user_activity(self, user_id: str) -> None:
    if user_id and self.runtime.lifecycle.manager:
        self.runtime.lifecycle.manager.track_task(self.update_user_stats(user_id))
```

通过 `self.update_user_stats(user_id)` 调用 async 方法得到协程对象，再传给 `track_task`（内部做 `asyncio.create_task`）。逻辑正确，但阅读时容易以为缺少 `await`。建议添加一行注释说明这是有意向后台派发 fire-and-forget 任务。
