## 🔴 Blocking

### B1. `persistence_schema.py` — ALTER TABLE 在表不存在或列已存在时可能抛出未捕获异常

- **文件**: `astrmai/infrastructure/persistence/persistence_schema.py`
- **位置**: `_init_db_sync()` 第 82–104 行（同步路径）和 `_init_db()` 第 118–140 行（异步路径）

两个路径均在 CREATE TABLE 之后立即执行 `ALTER TABLE ... ADD COLUMN` 迁移。如果某表因 SQLModel `create_all` 已创建（含所有列）后，ALTER 会因"duplicate column name"被捕获（catch 逻辑正确）。**但若 SQLModel 元数据中有表而 SQLite 文件缺失该表（例如磁盘文件被外部篡改），则 ALTER TABLE 会抛出 `sqlite3.OperationalError: no such table`，该异常不在 catch 范围内，会向上冒泡到 `logger.error(f"[AstrMai-Infra] ? {e}")` 但不会阻断启动**——然而此时 `_init_db` 已静默失败，表未创建，后续查询将报错。

**建议**: 在 ALTER 前用 `SELECT name FROM sqlite_master WHERE type='table'` 确认表存在，或统一走 SQLModel `create_all` 管理 DDL，废除双路径 ALTER。

### B2. `database_memory.py` — `save_event` 对已存在事件的更新覆盖 `memory_kind` / `source_layer` 字段归零

- **文件**: `astrmai/infrastructure/persistence/database_memory.py`
- **位置**: `save_event` 方法第 68–78 行

```python
if existing:
    existing.session_id = getattr(event, "session_id", "") or existing.session_id
    existing.narrative = event.narrative
    existing.emotion = event.emotion
    existing.importance = event.importance
    existing.emotional_intensity = event.emotional_intensity
    existing.reflection = event.reflection
    existing.tags = event.tags
    session.add(existing)
```

`existing.narrative = event.narrative` 等字段用了直接赋值（非 `or existing.xxx` 回退）。但 `event` 是一个 `MemoryEvent` SQLModel 实例，其默认值为 `narrative: str = Field(default="")`。如果调用方构造 `MemoryEvent` 时只传了 `event_id` 而未显式传 `narrative`/`emotion`/`reflection`，则这些字段取值 `""`，会**覆写**数据库中已有的值，造成数据丢失。

**建议**: upsert 逻辑应只在字段非空/非默认值时更新，或要求调用方传入完整对象。

## 🟡 Should-fix

### S1. `LaneManager._rotation_reason` — 锁外读 `_runtime_meta` 的 TOCTOU 风险（虽有注释担保，但极度脆弱）

- **文件**: `astrmai/infrastructure/runtime/lane_manager.py`
- **位置**: `_rotation_reason` 第 108–111 行

```python
async with self._meta_lock:
    meta = self._runtime_meta.get(lane_umo)
# 锁外读取安全：写操作是整体替换（= {...}）而非原地修改，
# meta 持有旧 dict 引用，后续 .get() 读取的是一致快照。
# 此处无 await 点，asyncio 不会切换协程，无 TOCTOU 窗口。
if not meta:
    return ""
```

注释论证了在当前实现下安全，但依赖两个隐式前提：(1) 写操作是原子赋值而非原地突变；(2) 读与 `.get()` 之间没有 `await`。任何未来重构（例如在 `if not meta` 前插入一个日志 `await`）都会引入竞态。约束性太强，无法被类型系统或 lint 工具检查。

**建议**: 将整个函数体放入 `async with self._meta_lock:` 内，或把 `self._runtime_meta.get(lane_umo)` 结果暂存局部变量后再释放锁。

### S3. `ChatRuntimeCoordinator.try_acquire_executor` — 释放时锁可能被误释放

- **文件**: `astrmai/infrastructure/runtime/chat_runtime_coordinator.py`
- **位置**: `release_executor` 第 37–46 行

```python
async def release_executor(self, chat_id: str) -> None:
    executor_lock: Optional[asyncio.Lock] = None
    async with self._lock:
        state = self._states.get(chat_id)
        ...
        executor_lock = state.executor_lock
    if executor_lock is not None and executor_lock.locked():
        executor_lock.release()
```

`executor_lock.locked()` 检查在 `release()` 前是一个单独的检查点——如果恰好有另一个协程在当前协程的 `locked()` 和 `release()` 之间调用了 `acquire()`，则 `release()` 会释放一个**刚刚被获取**的锁，导致另一个 critical section 的锁失效。

**建议**: 直接用 `try: executor_lock.release() except RuntimeError: pass`，去掉 `locked()` 守卫。

### S4. `PersistenceSchemaMixin._init_db` 与 `_init_db_sync` — `group_config` 字段被创建为 `TEXT` 但 `ChatState.group_config` 是 `Dict`

- **文件**: `astrmai/infrastructure/persistence/persistence_schema.py` 第 49 行 / 第 86 行
- `orm_models.py` 中 `ChatState.group_config` 类型注解为 `Dict[str, Any]`

SQLite TEXT 列存储 JSON 字符串是常见做法（`state_profile_persistence.py` 的 `save_chat_state` 确实做了 `json.dumps(state.group_config)`），但 ORM dataclass 的 `group_config` 字段缺少序列化注解/转换器。任何直写 `ChatState(group_config=...)` 的调用方若传入 dict 但未序列化，会触发 `TypeError: Object of type dict is not JSON serializable` 或存入 `"{}"`。

**建议**: 在 `ChatState` 上加 `@validator("group_config", pre=True)` 或改用 `sqlmodel.Field(sa_column=Column(JSON))`（虽 SQLite 不支持原生 JSON，但 SQLAlchemy 的 `JSON` 类型会自动做序列化）。

### S5. `EventBus._worker_loop` — 3 个 Worker 使用无界 `create_task`，出现异常时无恢复机制

- **文件**: `astrmai/infrastructure/runtime/event_bus.py`
- **位置**: `publish` 第 165–168 行

```python
if not self._workers_started:
    self._workers_started = True
    for _ in range(3):
        task = asyncio.create_task(self._worker_loop())
        self._background_tasks.add(task)
```

Worker 协程的 `while True` 循环遇到 `CancelledError` 会正常退出（`break`），但若有其他未捕获异常，worker 会静默消亡且没有重启逻辑。3 个工作协程全部消亡后，事件总线变为静默丢弃模式。

**建议**: 在 `_worker_loop` 外层套一个 `try/except` 重启循环，或改用 `asyncio.Queue` + `asyncio.TaskGroup` 管理。

### S6. `ObservabilityHub._append_trace_event` — `store.append` 异常被降级为 `logger.debug`

- **文件**: `astrmai/infrastructure/runtime/observability.py`
- **位置**: 第 262–267 行

```python
try:
    ...
    await store.append(payload)
except Exception as exc:
    logger.debug(f"[RuntimeObservabilityHub] raw trace append degraded: {exc}")
```

任何 `store.append` 异常都会被降级为 debug 日志，在生产环境（默认 log level INFO）中完全不可见。且 `store` 的类型仅为 `Any`，`append` 调用无类型检查——如果 `store` 不正确，数据丢失将完全无声。

**建议**: 至少使用 `logger.warning`，或增加一个计数器允许在第一次失败时告警而非静默丢弃。

## ⚪ Nits

### N1. `resolve_policy` 不会返回 `None`（已确认，消除 M2 担忧）

- `center.py` 第 100 行签名 `def resolve_policy(self, request: WorkloadRequest) -> WorkloadPolicy`（非 Optional）
- 函数体中每条路径都 `return WorkloadPolicy(...)`，无 `return None` 分支
- `WorkloadPolicy` 是一个 frozen dataclass 且所有字段都有默认值，所以即使 `request.models` 为空，`primary_model` 也只是空字符串而非引发异常
- **结论**: M2 报告中的 `compaction_providers` 可能使用了不同的代码路径，当前 `resolve_policy` 本身是安全的
