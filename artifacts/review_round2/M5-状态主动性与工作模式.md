## 2. 阻塞性问题（Blocking）

### B1. 异步锁定漏保护 — FrequencyController 字典竞争

| 位置 | `astrmai/state/energy/frequency_controller.py:55-60` |
|------|------------------------------------------------------|
| 问题 | `self._records_lock = asyncio.Lock()` 在第 55 行创建但从未被 `acquire()`。第 70-145 行的 `should_reply()`、`_get_record()`、`_record_message()`、`_record_reply()`、`_count_recent_replies()` 等所有方法均直接读写 `self._records` 字典而不加锁。多协程并发调用 `should_reply()` 时，`_records` 的写入/删除操作存在字典级竞争（CPython GIL 保护单字节操作但不保护 `list.append` 和 `list.remove`）。 |
| 建议 | 在每个读写 `self._records` 的方法开头 `async with self._records_lock` |

### B2. GroupReplyWaitManager 状态不一致

| 位置 | `astrmai/state/group_wait/group_reply_wait_manager.py` |
|------|--------------------------------------------------------|
| 问题 | `register_from_reply_event()`（第 81-115 行）中 `self._states[chat_id] = ...` 字典写入未持有 `self._states_lock`。同时 `handle_incoming_message()`（第 117-161 行）在移除键时也使用了 `self._states` 而不加锁。`cancel_timeout_task()` 读写 `self._timeout_tasks` 字典时仅在 `_arm_timeout_task` 内部受锁保护，但 `cancel_wait()` 直接调用时无序保护。异步环境下的 `dict.pop()` 非线程安全——两个协程可能同时 pop 同一 chat_id。 |
| 建议 | `register_from_reply_event()` 和 `handle_incoming_message()` 中所有对 `self._states` 的修改包裹 `async with self._states_lock`；`cancel_wait` 也应获取锁。 |

### B3. WakeupService 裸访问 config.life 属性

| 位置 | `astrmai/proactive/wakeup_service.py:76-82` |
|------|---------------------------------------------|
| 问题 | `self.config.life.silence_threshold`、`self.config.life.wakeup_min_energy`、`self.config.life.wakeup_cost`、`self.config.life.wakeup_cooldown` 均直接访问而不使用 `getattr`。若 `self.config` 为 `None`、无 `life` 属性、或 `life` 缺少这些属性，将在运行时抛出 `AttributeError`。第 95 行同样直接调用 `self.config.life.wakeup_cost`。 |
| 建议 | 全部改为 `getattr(getattr(self.config, "life", None), "wakeup_min_energy", 0.0)` 模式 |

### B4. RunOnce 期间 profile_semaphore 占用过高

| 位置 | `astrmai/proactive/proactive_task.py:416-448` |
|------|-----------------------------------------------|
| 问题 | `_run_profiling_task()` 获取 `_profile_semaphore`（容量 1）后，在 **整个 for 循环** 中保持锁定。循环对每个 active_state 调用 `_select_group_profile_target` → `record_profile_learning_touch`（I/O 操作），以及对每个 profile 调用 `_generate_nickname` 和 `_generate_persona_analysis`（LLM 调用）。这意味着在 LLM 生成期间整个 profiling 子系统被锁死，其他等待 profile 的服务（如 diary_service）可能饥饿。 |
| 建议 | 使用内部队列 + `asyncio.create_task()` 逐个处理 profile，或细粒度锁取代全局信号量。 |

## 3. 应修复问题（Should-fix）

### S1. ProactiveDispatcher runtime_coordinator 自检竞争

| 位置 | `astrmai/proactive/dispatcher.py:253-260` |
|------|------------------------------------------|
| 问题 | `_dispatch_locked()` 先将 `attention_gate.runtime_coordinator` 设为 `None`（第 255 行）来防止嵌套循环，调用 `inject_external_event` 后恢复（finally 块，第 260 行）。但假设期间其他协程也访问了 `attention_gate.runtime_coordinator`，会出现短暂状态异常。此外，若 `setattr` 恢复调用失败（如属性被删除），original 值丢失。 |
| 建议 | 考虑在调用期间使用 `contextlib.nullcontext` 或锁属性来替代副作用式临时移除 |

### S2. DecayService 和 DiaryService 主动调用 without lock

| 位置 | `astrmai/proactive/decay_service.py:22` |
|------|-----------------------------------------|
| 问题 | `self.state_engine.apply_natural_decay(state)` 在 `for state in self.state_engine.get_active_states()` 循环中直接调用。`apply_natural_decay` 修改 `state.energy` 和 `state.is_dirty`（有副作用）。但同一 `state` 可能在另一个协程的 `ChatStateService.mark_energy_consumed`（有锁保护）中被同时访问。由于 `get_active_states()` 返回引用而非快照，这些修改冲突可能导致 dirty 标记丢失或能量回退。 |
| 建议 | `DecayService` 内部应复制或锁定 chat_state_service 的锁链 |

### S3. DiaryService 文件写入非幂等

| 位置 | `astrmai/proactive/diary_service.py:26-30` |
|------|-------------------------------------------|
| 问题 | 循环内调用多个 `self.memory_engine.add_memory()` 和 `self.memory_engine.record_cognitive_feedback()`。若任何一次调用抛出异常（`except: logger.debug(...)` 仅记录不阻断），部分写入已完成，调用者无法回滚。 |
| 建议 | 考虑事务化或批量提交；或确保所有副作用幂等 |

### S4. GroupSigninService 无超时的网络调用

| 位置 | `astrmai/proactive/group_signin_service.py:96-103` |
|------|-----------------------------------------------------|
| 问题 | `await api.call_action("set_group_sign", group_id=str(group_id))` 没有 `asyncio.wait_for` 超时包装。如果底层 API 挂起，整个 `run_once` 循环被阻塞。 |
| 建议 | 添加 `asyncio.wait_for(..., timeout=10)` |

### S5. Router 混入了乱码日志

| 位置 | `astrmai/workmode/tools/handoff_registry.py:21` |
|------|--------------------------------------------------|
| 问题 | 日志字符串包含乱码 UTF-8 字节：`"鈿狅笍 鏈壘鍒?subagent_orchestrator锛屼繚鎸佺函闈欐€佹ā寮忋€?"` 和 `"璺熼殢鍏ㄥ眬"`。这表明原始字符串的非 ASCII 字符在保存时丢失了编码。在中文环境中，这些日志会输出为乱码。 |
| 建议 | 使用正确的 Unicode 转义或原始中文字符串 |

### S6. Router 缺少 `db_service` 属性但被引用

| 位置 | `astrmai/workmode/subagents/cron_agent.py:22` |
|------|------------------------------------------------|
| 问题 | `CronAgent` 的 `__init__` 接受 `db_service` 参数（第 22 行：`db_service: Any = None`），但仅存储在实例属性上，基类 `AstrMaiBaseSubAgent` 对其无引用。`_sync_dual_write` 方法（第 83 行）检查 `self.db_service` 是否为 `None`，但该属性仅在 `CronAgent` 作用域中定义——基类 `__init__` 不会调用子类 `__init__`（因使用了 `@dataclass`）。 |
| 建议 | 确认 Pydantic dataclass 继承了 `db_service` 字段。如果继承链不支持，则直接在 `call()` 中从 `context` 提取 db_service。 |

## 4. 轻微问题 / 建议（Nits）

### N1. AffectionRouter 的 `AstrMessageEvent` 占位导入

| 位置 | `astrmai/state/relationship/affection_router.py:4-7` |
|------|------------------------------------------------------|
| 问题 | `try: from astrbot.api.event import AstrMessageEvent; except ImportError: AstrMessageEvent = object`。这种失败降级到 `object` 的方法会完全禁用类型检查。如果在生产环境中 ImportError 被沉默，`isinstance(event, AstrMessageEvent)`（第 82 行）将永远为 `False`，所有事件类型都走 else 分支。 |
| 建议 | 去掉 try/except，让 import 失败时直接抛错，或提供真正的存根 |

### N2. `build_feedback` 浮点除法的边界精度

| 位置 | `astrmai/proactive/heartflow/feedback_bridge.py:49` |
|------|-----------------------------------------------------|
| 问题 | `avg_interest = sum(...) / len(pulses)`，虽然 `pending_pulses` 确保 `len(pulses) > 0`，但如果所有 pulse 的 `urgency` 都是 0.0，返回 `0.0` 是合理的。无实际风险，标记为边界意识。 |

### N3. `evaluate_proactive_rhythm` 全局状态副作用

| 位置 | `astrmai/proactive/rhythm.py:74-87` |
|------|-------------------------------------|
| 问题 | `_log_tz_diagnostic_once` 使用模块级全局变量 `_TZ_DIAGNOSTIC_LOGGED` 来控制只记录一次。这在单元测试中会导致跨测试副作用（第一个测试后所有测试不再输出时区诊断）。 |
| 建议 | 测试中用 `unittest.mock.patch` 或改为实例级状态 |

### N4. `CronHeartbeatGuard._revive_job` 每次心跳都导入

| 位置 | `astrmai/workmode/cron_guard/heartbeat.py:103` |
|------|-------------------------------------------------|
| 问题 | `from astrbot.core.db.po import CronJob` 位于方法体内，每次心跳循环（60 秒一次）都重新导入。虽然 Python 有缓存，但 `from` 导入仍然进行模块缓存查找和赋值。 |
| 建议 | 移到模块顶层的 `try/except ImportError` 中 |

### N5. `_collect_quiet_summary` 在 None 上调用 `getattr`

| 位置 | `astrmai/proactive/proactive_task.py`（通过 chat_loop_kernel 引用） |
|------|--------------------------------------------------------------------|
| 问题 | `getattr(owner, "config", None)` 在 `owner` 可能为 `None` 时确实安全，但阅读者容易误以为 `getattr` 可以用来调用方法。建议在循环中先过滤 `None`。 |
