## 🔴 Blocking（阻止发布）

### B1. `learning/evolution_manager.py:238` — `get_active_patterns` 同步方法在事件循环中调用 `asyncio.run()` 必崩

**文件**: `astrmai/learning/evolution_manager.py`  
**位置**: `get_active_patterns_canonical()` 方法内

```python
return asyncio.run(service.render_active_patterns(chat_id, limit=limit))
```

该方法被同步包装器 `get_active_patterns`（`get_active_patterns = get_active_patterns_canonical`）暴露。当当前线程已有运行中的事件循环时（这是异步框架的常态），`asyncio.run()` 抛出 `RuntimeError: asyncio.run() cannot be called from a running event loop`。

**修复方向**: 将该方法改为纯 `async`，或使用 `asyncio.get_running_loop().create_task()` + future 模式；调用方也需改为 `await`。

---

### B2. `memory/injection_service.py` + `retrieval_service.py` — 持续设置已弃用字段 `retrieve_keys`，每次调用触发 `DeprecationWarning`

**文件**: 
- `astrmai/memory/services/memory_injection_service.py` — `build_bundle()` 方法
- `astrmai/memory/services/memory_retrieval_service.py` — `_build_trace_summary()` 方法

`MemoryQuery.__post_init__` 在 `retrieve_keys` 非空时发出 `DeprecationWarning`（堆栈级别 2）。但 memory 内部代码就是最大的调用方：
- `injection_service.py` 构造 `MemoryQuery` 时传入 `retrieve_keys=list(retrieve_keys)`
- `retrieval_service.py` 读取 `getattr(query, "retrieve_keys", [])`

这导致每次记忆注入都在 stderr 输出弃用警告，污染日志且可能触发某些监听器的告警。

**修复方向**:  
  (a) 移除 `retrieve_keys` 的 `__post_init__` 警告，或  
  (b) 将所有内部调用显式传空列表 `retrieve_keys=[]`，只在外部 API 入口保留警告。

---

### B3. `memory/processor.py:1` — 文件头部包含指向不存在路径的中文开发笔记

**文件**: `astrmai/memory/services/memory_processor.py`

文件全局作用域包含多处如下注释：
```
# 位置: astrmai/memory/processor.py -> MemoryProcessor 类下
```
该文件真正的路径是 `astrmai/memory/services/memory_processor.py`，而非注释中的 `astrmai/memory/processor.py`。这表明代码曾从旧路径迁移至此，残留注释未清除。这些注释在运行时虽无影响，但**极易误导后续开发者**。

**修复方向**: 清理所有 `# 位置:` 注释。

---

### B4. `memory/write_service.py:18-25` — `should_skip_content` 过于激进，将正常 JSON 对话内容全部丢弃

**文件**: `astrmai/memory/services/memory_write_service.py`

```python
if text.startswith("{") or text.startswith("```json"):
    return True
```

任何以 `{` 开头的用户消息（例如 `{我想吃火锅}`、`{明天几点见面}` 等自然对话）都会被跳过，不会写入记忆。这个规则的本意是过滤 JSON 格式的系统消息，但 `{` 是常见的中文聊天起始字符，误杀率极高。

**修复方向**: 改为检查完整 JSON 解析 + 确保是结构化的元数据格式（如 `{"type": ... }`），而非仅检查首字符。

---

### B5. `memory/engine.py:187-193` — `start_background_tasks` 中对 `db_service` 的访问可能为 `None`

**文件**: `astrmai/memory/services/memory_engine.py`

```python
async def start_background_tasks(self):
    raw_trace_store = getattr(getattr(self, "db_service", None), "raw_trace_store", None)
    ...
    event_bus=getattr(getattr(self, "db_service", None), "event_bus", None) or getattr(self.gateway, "event_bus", None),
```

`self.db_service` 在 `__init__` 中被初始化为 `None`，且从未在 `initialize()` 中赋值。`start_background_tasks()` 被调用时若外部未注入 `db_service`，则 getattr 链不会报错但会静默返回 `None`，导致 `MemoryObserver` 和 `event_bus` 以降级模式工作，trace 丢失。

**修复方向**: 在 `initialize()` 或 `__init__` 中明确赋值 `self.db_service`，或 `start_background_tasks` 醒式检查并在缺失时打 warning。

---

### B6. `learning/evolution_manager.py:120-130` — `_append_message_log` 存在同步/异步双路径，某些 db 实现可能无 `add_message_log_async`

**文件**: `astrmai/learning/evolution_manager.py`

```python
async def _append_message_log(self, *, group_id, sender_id, sender_name, content):
    if hasattr(self.db, "add_message_log_async"):
        await self.db.add_message_log_async(...)
        return
    self.db.add_message_log(...)  # 同步调用，在 async 函数中做阻塞 IO
```

该模式在多个方法中重复（`_load_unprocessed_logs`, `_mark_logs_processed`）。当 `self.db` 没有 `_async` 版本时，会执行同步数据库调用，阻塞事件循环。

**修复方向**: 统一使用 `asyncio.to_thread()` 包裹同步调用，或要求 `db` 必须暴露 async 接口。

## 🟡 Should-fix（建议修复）

### S1. 数据联通: `learning/evolution_manager.py` → `memory/engine.py` 的事件桥接仅单向

`EvolutionManager._publish_learning_event()` 发布 `learning.bot_reply_recorded` / `learning.mining_completed` 到 `event_bus`。`MemoryEngine` 仅在 `on_learning_*` 方法中**记录到内部缓存**，并未实际触发任何检索或索引操作。

- `on_learning_bot_reply_recorded`: 只调用 `_remember_learning_event` 追加到 `_learning_event_history` 列表
- `on_learning_mining_completed`: 同上

这意味着 learning 模块完成模式挖掘/黑话挖掘后，**memory 侧不会触发任何索引更新或缓存失效流程**。新写入的 patterns/jargons 可能在 retrieval 中延迟出现在搜索结果中。

**修复方向**: 在 `on_learning_mining_completed` 中触发 `index_projector` 重建，或至少通知 `v2_store` 更新其 FTS 索引。

---

### S2. `memory/tool_service.py:142-148` — `omni_query` 内中文硬编码只支持简体中文

**文件**: `astrmai/memory/services/memory_tool_service.py`

```python
if entity == current_sender_name or entity in {"我", "自己", "当前用户"}:
```

这些字符串仅对简体中文用户有效，英文/日文/繁体用户会 miss。此外 `get_user_profile` / `get_profile_by_name` 接口在 `db_service` 上是否存在仅在运行时 hasattr 检查，**无文档约定**。

**修复方向**: 将语言相关的字符串放入配置，或改用语义判断（如 `entity == current_sender_name`）。

---

### S3. `memory/retrieval_service.py:322-329` — `_call_deep_json` 捕获 `TypeError` 但不处理，可能隐藏真正错误

```python
try:
    response = await gateway.call_data_process_task(prompt=prompt, is_json=True)
except TypeError:
    response = await gateway.call_data_process_task(prompt, is_json=True)
```

当第一次调用因**非 TypeError** 的原因失败时（如网络超时），异常不会被捕获，上层逻辑退化。`except TypeError` 应缩小范围或记录日志。

**修复方向**: 仅当已知某个特定网关版本接口签名不同时才使用此 fallback，否则移除。

---

### S4. `memory/engine.py` 多处 `@staticmethod` 但以 `cls.method()` 形式被调用

- `_feedback_prefix` → 被 `@classmethod _format_cognitive_feedback_content` 调为 `cls._feedback_prefix()`，无害
- `_normalize_feedback_tags` → 同上，`cls._normalize_feedback_tags()`，无害

严格上 `@staticmethod` 方法通过 `cls.` 调用是合法的，但语义上 `@classmethod` 更准确。当前写法不会触发错误，但属代码异味。

## 结论

**级别**: Blocking（6 个阻止级问题，3 个应修级）
