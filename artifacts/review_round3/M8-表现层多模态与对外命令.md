## 应修复 (Should-fix)

### SF-1. `IngressDecision` / `MessageScope` 类存在两份完全相同的副本，一份是死代码

**文件:**
- `astrmai/presentation/dto/message_scope.py` — **活代码，被广泛引用**
- `astrmai/conversation/contracts/message_scope.py` — **死代码，无任何模块导入**

**问题:** 两个文件定义了完全相同的数据类 `IngressDecision` 和 `MessageScope`（slot frozen dataclass，方法签名一致）。我通过 `search_content` 验证了全代码库中没有任何模块从 `...contracts.message_scope` 导入这两个类——所有内部依赖（`command_guard.py`, `dedupe.py`, `permission_guard.py`, `poke_handler.py` 以及 `plugin_facade.py`）都从 `...presentation.dto.message_scope` 导入。

**风险:** 双副本会在后续维护中悄然分歧（一份加了字段而另一份没加），导致运行时 `isinstance` 检查或 duck-typing 意外失败。属于典型的"坏味道"。

**建议:** 删除 `astrmai/conversation/contracts/message_scope.py`，将所有引用（包括 `contracts/__init__.py`）改为 re-export presentation DTO 版本，或者直接删除后更新 `contracts/__init__.py` 的 `__all__`。

---

### SF-2. `enter_sys3_direct()` 作为 async generator 的 yield 行为不一致

**文件:** `astrmai/app/plugin_facade.py` 第 305–342 行（`enter_sys3_direct` 方法）

**问题:** 该方法声明为 `async def` 且使用了 `yield`（因此是 async generator），但 **仅在禁用分支、空查询分支抛出 yield**，而 **正常执行路径直接调用 `handle_reply()` 后 return，并不 yield 任何值**。

调用方 (`work_mode.py:handle_work_mode`)：

```python
async for result in facade.enter_sys3_direct(event):
    yield result
```

这意味着正常执行时 `async for` 循环零次迭代，没有任何 result 被 yield 回 astrbot 框架。虽然通过 `handle_reply()` 直接发送了回复（技术上能工作），但割裂了 yield-based 的事件链，破坏了一致性。

**风险:** 
- 任何未来依赖 yield chain 做后处理（如统计、日志、hook）的路径会被静默跳过
- 调试时不易察觉——消息发出去了，但 yield 链中断

**建议:** 统一风格：要么全部通过 `yield event.plain_result(...)` 返回，消除对 `handle_reply` 的直接调用；要么将方法改为纯 async（不 yield），调用方也改为 `await`。

## 建议修复 (Should-fix / Low)

### SF-3. `transform_gif()` 中存在可疑的 ASCII 往返编码

**文件:** `astrmai/multimodal/image_pipeline.py` 第 55 行

```python
gif_data = base64.b64decode(gif_base64.encode("ascii", errors="ignore").decode("ascii"))
```

**问题:** `gif_base64` 在传入时已经是一个 `str`。这里先 `.encode("ascii", errors="ignore")` 转为 bytes，再 `.decode("ascii")` 转回 str，然后才传给 `base64.b64decode`。对于合法的 base64（纯 ASCII），这一往返是无操作（no-op）。但如果 `gif_base64` 意外包含非 ASCII 字符（极罕见），`errors="ignore"` 会静默丢弃它们，生成损坏的 base64 载荷。

**风险:** 很低。Base64 理论上只含 ASCII。但防御性编码应该显式检查或抛出异常，而非静默丢弃。

**建议:** 删除多余的 `.encode("ascii", errors="ignore").decode("ascii")`，直接 `base64.b64decode(gif_base64)`。如果担心异常，用 `try/except` 包裹。

## 轻微 (Nit)

### N-1. `message_entry.py` / `result_sniffer.py` 缺失 `__all__`

**文件:**
- `astrmai/presentation/events/message_entry.py`
- `astrmai/presentation/events/result_sniffer.py`

**问题:** 同目录下的 `error_interceptor.py`、`startup_hooks.py` 和 `__init__.py` 都定义了 `__all__`，但这两个模块没有。`message_entry.py` 导出 `handle_global_message`，`result_sniffer.py` 导出 `sniff_external_plugin_results`，缺失 `__all__` 不会导致运行时错误（因为它们是直接被 `plugin_facade.py` 按名导入的），但不符合模块内约定一致。

**建议:** 为两个文件补上 `__all__`。

---

### N-2. `presentation/events/__init__.py` 几乎为空

**文件:** `astrmai/presentation/events/__init__.py`

**内容:** 仅有一行 docstring，无任何 re-export。

**问题:** 不产生功能缺陷。但 `events` 包目前完全不被 `from .events import ...` 方式使用（`plugin_facade.py` 直接导入子模块），这种模式使得包级 `__init__.py` 形同虚设。若未来有人尝试 `from .events import handle_global_message` 将失败。

**建议:** 从 `__init__.py` re-export 所有四个事件函数，或维持现状但加注释说明意图（"只做直接导入，不通过 __init__ 聚合"）。

---

### N-3. `send_meme` 函数存在两套发送路径，调用方上下文规则不透明

**文件:** `astrmai/multimodal/meme/meme_sender.py` 第 16–27 行

**问题:** 函数根据 `context` 参数是否为 `None` 走两套不同的发送逻辑：
- `context` 非 `None` → 通过 `context.send_message()` 发送
- `context` 为 `None` → 通过 `event.make_result() + event.send()` 发送

这在 API 契约上不够明确。调用方 (`reply_post_send.py`) 总是传入 `context`，所以第二条路径目前不会触发。但未来若有调用方误传 `context=None`，行为会静默切换。

**建议:** 将 `context` 设为必需参数（或拆成两个函数），让两套发送逻辑的选择显式化。
